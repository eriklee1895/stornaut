## 1. Decision and Ownership Boundary

The completed ASID prerequisite made the shared claim evidence truthful but did
not implement ii-b2 behavior. The accepted ii-b2 contract requires the helper
to replace its original claim deadline with a release deadline, accept one exact
release on the same attested connection epoch, wait for reply dispatch before
arming bounded helper exit, and make every already-fired timer race fail closed.

The current live implementation cannot express that contract:

- `LifecycleMachineRetirementEscrow` has only `empty`, `recorded` and
  `consumed`; a successful claim consumes the escrow immediately;
- the helper schedules the original claim deadline as an uncancellable global
  `asyncAfter` closure that always calls `exit(0)`, even after the escrow is no
  longer awaiting claim; and
- current JSON v2 claim/XPC types have neither the shared request digest,
  connection epoch nor monotonic epoch deadline required by STNC v1.

Changing only the existing escrow would create two competing truths: a new
state machine plus the old unconditional helper timer. Making broad
`StornautLifecycle` depend on `StornautInvestigationHandoffContract` would also
carry the complete machine-claim wire through the ordinary App's shared static
package graph. Dead stripping is not an authority or topology argument.

ii-b2 therefore remains split:

```text
ii-b2a  Lifecycle-internal typed state/deadline primitive, not connected
ii-b2b  shared-wire adapter + existing escrow/XPC/helper/Machine migration
```

ii-b2a adds one new package/internal source to the existing Lifecycle target.
It is physically compiled with Lifecycle but is unreferenced by current product
code, exposes no public API and contains no wire, XPC, scheduler, process or exit
authority. A separate target was considered and rejected for this checkpoint:
the helper is an external Xcode target, so a new package target would force
premature public/product linkage. ii-b2b must instead add a dedicated server-side
adapter target that depends one-way on both `StornautLifecycle` and
`StornautInvestigationHandoffContract`. The helper may consume that adapter;
broad Lifecycle and the ordinary App must not gain a HandoffContract dependency.
SwiftPM Machine may use it only in injected, non-native migration tests. The
adapter must not own `NSXPCConnection`, service selection, helper path/signing
admission, client claim/release dispatch or helper-exit observation, and it must
not enter `StornautInvestigationMachineDriverSupport` or the native driver final
Mach-O. ii-b4 remains the sole fixed NSXPC client owner. The adapter can compose
the package-scoped core inside the migrated server escrow without relying on
dead stripping. Its package product, Xcode helper linkage, ordinary-App absence
and diagnostic/native final-artifact allowlists belong to the later ii-b2b
preflight, not ii-b2a.

## 2. Deterministic Domain Contract

The new source is
`Sources/StornautLifecycle/LifecycleMachineRetirementEscrowDeadlineState.swift`.
All declarations are `package` or internal, `Sendable` where applicable and
non-`Codable`. It imports Foundation only. It neither reads a clock nor schedules
a task; callers supply already-observed time and apply returned typed effects.

### 2.1 Opaque identities and observations

The core defines validated, non-secret semantic values rather than reusing or
duplicating wire codecs:

- reservation UUID, nonzero and generated by the future adapter;
- request-binding SHA-256, exactly 32 raw bytes;
- helper-identity SHA-256, exactly 32 raw bytes;
- claim connection-epoch UUID, nonzero;
- release-challenge UUID, nonzero and fresh for the release transition;
- handle/config validity plus claim-request issued-at and valid-before values as
  positive UTC microseconds in `Int64`; and
- monotonic observation as an absolute `UInt64` nanosecond value plus wall UTC
  microseconds.

No handle token, path, configuration bytes, auth value, PID, audit token, XPC
object or process handle enters the core. ii-b2b owns strict conversion from the
existing Lifecycle domain and the shared HandoffContract.

### 2.2 State model

The state is closed and one-shot:

```text
empty
  -> claimDeadlinePendingArm
  -> awaitingClaim
  -> releaseDeadlinePendingArm
  -> claimedAwaitingRelease
  -> releasedAwaitingReplyDispatch
  -> postReplyExitPendingArm
  -> releasedExitScheduled
  -> terminal
```

The pending-arm states are mandatory. Scheduling is an external effect and can
fail after a state transition. The core must not claim ownership of an unarmed
timer or permit claim/release progress before the matching deadline ticket is
confirmed armed. An exact matching arm failure transitions terminal. A stale
arm failure is a no-op; a stale arm success returns a cancel effect for the
external timer that was actually created. Neither can affect a newer generation.

`releasedAwaitingReplyDispatch` is distinct from `releasedExitScheduled`. Release
atomically consumes `claimedAwaitingRelease`, invalidates the release timer and
computes one immutable post-reply exit deadline from the release-acceptance
observation, but it creates no exit ticket and produces no schedule effect. Only
an explicit reply-dispatch commitment after the external reply invocation
returns may create/arm a ticket for that retained deadline.

Terminal reasons are a closed enum and distinguish at least:

- claim deadline expired;
- release deadline expired;
- post-reply exit due;
- cancellation;
- matching connection invalidation;
- binding mismatch;
- duplicate or replay;
- invalid/expired time observation;
- checked-arithmetic overflow;
- deadline arm failure;
- scheduler fired early;
- reply dispatch failure; and
- post-reply deadline already expired before dispatch commitment.

Terminal state is immutable. It cannot record, claim, release, dispatch or arm
again. Repeated cancellation/invalidation/deadline callbacks are idempotent and
cannot resurrect state. A duplicate/replayed protocol transition on the matching
reservation/connection consumes the attempt terminally as `duplicateOrReplay`,
including a concurrent claim/release loser that arrives after one winner. A
foreign digest/helper/epoch/deadline at the corresponding admissible transition
consumes terminally as `bindingMismatch`. Only a foreign connection invalidation
event and a stale timer/arm callback identified by its ticket are harmless.

### 2.3 Deadline tickets and effects

Every scheduled deadline has one immutable ticket containing:

- kind: claim, release or post-reply exit;
- strictly increasing checked generation;
- reservation UUID; and
- exact absolute monotonic deadline.

Transition results return only typed `schedule` and `cancel` effects plus the
admitted deadline/value needed by the future adapter. Effect execution always
occurs after the core releases its linearization lock. The core API explicitly
owns four external-effect acknowledgements:

```text
armSucceeded(ticket)
armFailed(ticket)
deadlineFired(ticket, observation)
replyDispatchFailed(reservation, connectionEpoch)
```

For a matching pending-arm ticket, `armSucceeded` enters the corresponding armed
state and `armFailed` enters terminal `deadlineArmFailure`. If cancellation,
invalidation or a deadline callback won while scheduling was in flight, a later
stale `armSucceeded` returns a typed `cancel(ticket)` effect so the now-real
external timer never becomes ownerless; stale `armFailed` is a no-op.

`deadlineFired` may arrive before `armSucceeded` because a scheduler can invoke a
callback immediately. It carries a monotonic/wall observation and may terminally
win from the matching pending-arm or armed state only when `now >= deadline`. A
matching early callback is terminal `schedulerFiredEarly`. Every later
`armSucceeded` for that ticket returns `cancel(ticket)`. A callback for a
replaced/consumed ticket returns `stale` and makes no state change.

The future schedule adapter keys its cancellation handle by the complete ticket.
`cancel(ticket)` is repeatable and best effort only; every callback still
re-enters the core and matches current state, kind, generation, reservation and
deadline. Neither an arm acknowledgement nor a callback executes while the core
lock is held. Before arming can make a callback visible, the future adapter must
register a ticket-keyed cancellation slot. If the callback/core produces a
cancel effect before the concrete scheduler handle is returned, the slot records
the pending cancel and applies it immediately when the handle arrives. This
adapter obligation is ii-b2b work; ii-b2a tests the typed ordering/effects only.

## 3. Time and Deadline Arithmetic

Monotonic nanoseconds are the only protocol deadline domain. Wall UTC is a
separate validity cap and is never used as a protocol clock. Values are integers,
not `Date`/`Double`, so ii-b2a has no rounding, NaN or infinity ambiguity.
ii-b2b performs the single checked domain conversion.

The two wall bounds are not interchangeable. Reservation stores the existing
handle/config `validBefore`; the original claim timer maps that bound exactly
once into `retainedHandleMonotonicCap` from one paired observation. Later
wall-clock rollback can never extend that cap. A claim separately supplies
`requestIssuedAt` and `requestValidBefore`; the core requires
`issuedAt <= claimWallNow < requestValidBefore <= handleValidBefore` and a
positive request window no greater than exactly 15 seconds.

Each transition also computes a fresh handle wall cap from its paired observation
and uses the minimum of that cap and the retained cap. Thus wall rollback cannot
extend authority and a forward jump immediately shortens it. Wall or monotonic
observation rollback is terminal fail-closed; a wall observation at or beyond
validity is expired. The request window controls claim admission only: a claim
must be observed before `requestValidBefore`, but a successfully admitted claim's
release window is not truncated by the now-consumed request window. This matches
the governing parent formula; release remains bounded by five seconds, the epoch
deadline and the retained/fresh handle/config caps. At successful claim:

```text
releaseDeadline = min(
    claimNow + 5_000_000_000,
    epochDeadline,
    retainedHandleMonotonicCap,
    freshHandleWallCap
)
```

At release acceptance, the core freezes the later post-reply deadline:

```text
postReplyExitDeadline = min(
    releaseAcceptedNow + 5_000_000_000,
    retainedEpochDeadline,
    retainedHandleMonotonicCap,
    releaseAcceptedFreshHandleWallCap
)
```

Both five-second constants are exact. Every subtraction, microsecond-to-
nanosecond multiplication, generation increment and absolute addition is
checked; saturation is forbidden. The chosen deadline must be strictly greater
than observed monotonic time. For claim/release/reply transitions,
`now == deadline` is expired; one tick before is admissible.

## 4. Transition and Race Requirements

Tests-first implementation must directly prove all of the following.

### 4.1 Normal path

1. `empty -> claimDeadlinePendingArm -> awaitingClaim` binds the reservation,
   handle/config wall validity, exact claim ticket and generation.
2. An admitted claim binds request digest, helper digest, connection epoch and
   epoch deadline, proves exact issued-at/valid-before request bounds, cancels
   the claim ticket and produces the exact release deadline/ticket. The retained
   binding also includes the original claim-challenge UUID so the later release
   challenge can be proved fresh.
3. Release is accepted only in `claimedAwaitingRelease` with exact retained
   digest/helper/epoch/deadline and one fresh challenge. It cancels the release
   ticket, freezes the post-reply deadline from `releaseAcceptedNow`, and enters
   `releasedAwaitingReplyDispatch` with no exit ticket or schedule effect. The
   returned released value already contains that immutable deadline.
4. The external adapter invokes the release reply closure first. Only after that
   invocation returns does it call `replyDidDispatch(observation)`, which
   requires nondecreasing wall/monotonic observations, wall validity still open
   and `replyDispatchNow < retainedPostReplyExitDeadline`; it creates the exit
   ticket using that exact retained deadline. Equality or lateness is terminal
   without a ticket. After the ticket is armed, the state is
   `releasedExitScheduled`. No exit ticket or schedule effect exists before
   `replyDidDispatch`, and reply latency can never extend the deadline.
5. The exact exit callback produces terminal `postReplyExitDue`; it never calls
   `exit`, signals a process or schedules work itself.

### 4.2 Bounds and failures

- claim/release/reply at one tick before the deadline succeeds; equality and
  later observations fail terminally;
- the epoch deadline and wall validity can each independently be the minimum;
- expired/zero wall remainder, nonpositive interval, checked addition/
  multiplication/generation overflow and invalid observation fail closed;
- wall or monotonic observation rollback fails terminally and can never extend
  the retained handle cap;
- claim-request validity later than handle validity, or a release challenge
  equal to the retained claim challenge, connection epoch or reservation UUID,
  fails closed;
- matching arm failure from each pending-arm state is terminal;
- matching early scheduler fire is terminal and a later arm success returns
  cancel for the externally created timer; and
- reply-dispatch failure from the waiting state is terminal and produces no exit
  ticket.

### 4.3 Linearization and stale callbacks

- claim versus claim-deadline and release versus release-deadline each have one
  linearization winner;
- sixteen concurrent valid claims have at most one admitted claim result; the
  first duplicate/replay loser terminally consumes the attempt, as required by
  the parent contract;
- stale claim callbacks after claim/cancel, stale release callbacks after
  release/dispatch and repeated callbacks make no state change;
- release versus cancellation/invalidation and reply dispatch versus
  cancellation/invalidation each have one winner;
- cancellation is covered from every live state and is idempotent after terminal;
- foreign connection invalidation does not terminate another epoch; and
- a ticket's best-effort external `cancel` racing its callback cannot bypass the
  state/generation/deadline match.
